# Единый выбор «вендор + аккаунт» для агента

Дата: 2026-09-08
Статус: дизайн согласован, реализация не начата
Ветка: feat/adapter-account-picker

## 1. Проблема

Сегодня привязка агента к конкретной учётной записи вендора делается в два приёма и в двух разных местах формы:

1. сверху выбирается вендор — поле «Adapter type», ui/src/components/AgentConfigForm.tsx:1378;
2. снизу, в редакторе переменных окружения, вручную прописывается переменная-путь к «дому» учётки: CODEX_HOME для Codex, CLAUDE_CONFIG_DIR для Claude.

Переключить агента на другую учётку того же вендора можно только правкой этой переменной или полным перелогином. Для Claude в текущей инсталляции это вообще делается вне Paperclip — симлинками ~/.claude на ~/.claude-accounts/subN.

Нужен один список вида:

    codex  — xxx@gmail.com
    codex  — yyy@gmail.com
    claude — zzz@gmail.com

Выбор строки мышкой переключает агента на нужную учётку нужного вендора. Плюс возможность добавлять и удалять учётки, и не только для Codex.

## 2. Что уже есть в коде

Это не с нуля. Большая часть механики существует, но не выведена в интерфейс.

**Учётки уже существуют, но неявно.** После device-login промоушен создаёт отдельный каталог-«дом» учётки и заводит секрет компании с именем CODEX_HOME_<handle>, где handle — это account_id из auth.json. Имя формируется в server/src/routes/agents.ts:807, санитайзер handle — packages/shared/src/account-handle.ts. Никакого реестра учёток нет: список существует только как набор секретов с общим префиксом.

**Email уже извлекается.** packages/adapters/codex-local/src/server/quota.ts:104-107 читает chatgpt_user_email и profile.email из токена; результат уже показывается в проверке адаптера как «Logged in as …» — test.ts:307. Нигде не сохраняется.

**У Claude идентичность лежит на диске в готовом виде.** В <config-dir>/.claude.json есть блок oauthAccount с полями accountUuid (стабильный ключ) и emailAddress (подпись). Проверено на ~/.claude-accounts/sub1.

**Claude уже уважает явный CLAUDE_CONFIG_DIR** в локальном лане — packages/adapters/claude-local/src/server/execute.ts:456. Это значит, что для локальных ранов переключение учётки не требует изменений в auth-пути адаптера.

**Пер-аккаунтные дома реализованы только у codex-local и grok-local** — у них есть src/server/adapter-auth-promotion.ts. У claude-local каталог конфига компанейский, не пер-аккаунтный: packages/adapters/claude-local/src/server/claude-config.ts:130.

**Плагинная система не покрывает форму агента.** Слоты ui/src/plugins/slots.tsx:152 — это page, routeSidebar, detailTab, taskDetailView, contextMenuItem, commentAnnotation, commentContextMenuItem, projectSidebarItem, toolbarButton. Точки встраивания внутрь AgentConfigForm нет, поэтому пикер — правка ядра, а не плагин.

## 3. Цели и не-цели

Цели:

- один список «вендор — учётка», переключение одним кликом;
- добавление учётки без ручной правки переменных: через логин или регистрацией существующего каталога;
- удаление учётки с защитой от поломки привязанных агентов;
- механизм общий для вендоров, а не только для Codex;
- полное сохранение текущего поведения: агенты с руками прописанным CODEX_HOME продолжают работать без миграции.

Не-цели:

- переписывание auth-путей адаптеров;
- изменение приоритетов разрешения кредов (auth-precedence);
- единый логин-флоу для всех вендоров;
- перенос учёток между компаниями.

## 4. Дизайн

### 4.1. Модель

Учётка = тройка (adapterType, handle, homeDir).

Источник истины не меняется: homeDir по-прежнему хранится в секрете компании со значением-путём, и именно секрет остаётся тем, на что ссылается конфиг агента. Второй источник истины с путями сознательно не заводится — он неизбежно разойдётся с секретами при ручных правках.

Добавляется только слой подписи: таблица метаданных с ключом (companyId, adapterType, handle) и полями label, lastSeenAt. Ни путей, ни секретов она не хранит. При промахе подпись дочитывается с диска и кэшируется.

### 4.2. Capability адаптера

Новая необязательная capability accountBinding:

    interface AdapterAccountBinding {
      envKey: string;        // CODEX_HOME | CLAUDE_CONFIG_DIR | GROK_HOME
      secretPrefix: string;  // CODEX_HOME_ | CLAUDE_CONFIG_DIR_ | GROK_HOME_
      readIdentity(homeDir: string): Promise<{ handle: string; label: string | null } | null>;
    }

Реализации:

- codex-local: handle = tokens.account_id, label = chatgpt_user_email либо profile.email (переиспользует существующий парсер quota.ts);
- claude-local: handle = oauthAccount.accountUuid, label = oauthAccount.emailAddress из .claude.json;
- grok-local: по образцу codex.

Адаптер без этой capability просто не даёт строк в списке — так вендоры без учёток (API-key-only) остаются как есть.

Побочный полезный эффект: хардкод префикса CODEX_HOME_ в server/src/routes/agents.ts:807 заменяется чтением capability, и путь становится общим.

### 4.3. Сервер

Новый сервис-модуль отдельным файлом плюс роут:

    GET /companies/:companyId/adapter-accounts

Ответ — плоский список:

    { adapterType, handle, label, secretName, boundAgents, status }

Сборка: перечислить секреты компании, отобрать те, чьё имя начинается с secretPrefix зарегистрированных адаптеров, взять подпись из метаданных, при промахе — прочитать с диска через readIdentity. boundAgents считается по агентам, у которых adapterConfig.env[envKey] ссылается на этот секрет. status — active либо needs_login, если дом недоступен или креды непригодны.

Добавление учётки, два пути:

1. существующий device-login, запущенный с уже выбранным вендором — он и сегодня умеет заводить вторую учётку, просто это не выведено в UI;
2. регистрация существующего каталога — путь проверяется на пригодность через readIdentity, затем создаётся секрет с именем <secretPrefix><handle>. Это закрывает ровно кейс с готовыми ~/.claude-accounts/subN без перелогина.

Удаление учётки обязано идти через уже существующую защиту: fail-closed скан всех секретов компании на ссылки в этот каталог (логика описана в server/src/routes/agents.ts:323 и ниже) плюс отказ при boundAgents больше нуля. Каталог удаляется только после обеих проверок.

### 4.4. UI

Новый отдельный компонент-пикер. В AgentConfigForm он встраивается в одну точку — на месте поля «Adapter type», строка 1378. Размер файла (3680 строк) — причина выносить всю логику наружу, а не расширять форму на месте.

Список сгруппирован по вендору. Строки: «codex — xxx@gmail.com». Дополнительные пункты: «учётка по умолчанию для компании» (текущее поведение при пустой переменной) и «войти в новую учётку».

Выбор строки формирует один PATCH агента, который пишет и adapterType, и биндинг adapterConfig.env[envKey] на секрет учётки. То есть пикер пишет ровно то поле, которое сегодня заполняется руками.

Ручной редактор переменных остаётся без изменений и служит advanced-путём. Если у агента переменная указывает на путь, не совпадающий ни с одной известной учёткой, пикер показывает «произвольный путь» и не перетирает значение.

### 4.5. Фазы

Фаза 1 — чтение и переключение: capability для codex, claude, grok; листинг; пикер. Ничего в рантайме не меняется.

Фаза 2 — добавление и удаление учёток из UI.

Фаза 3 — sandbox-стейджинг дома учётки для Claude и подключение остальных вендоров, по одному, за флагом.

## 5. Оценка риска регресса

**Фаза 1 — риск в рантайме близок к нулю.** Ключевой аргумент: пикер записывает то же самое поле adapterConfig.env[envKey], что человек заполняет руками сегодня. Пути исполнения — codex-home.ts, auth-precedence.ts, acp.ts, execute.ts — не меняются вообще. Реальная зона риска одна: AgentConfigForm.tsx и его тестовый хвост, включая OnboardingWizard.adapters.test.tsx. Смягчение — вынос компонента наружу и одна строка встраивания.

**Фаза 2 — средний риск.** Добавление почти бесплатно. Опасна кнопка удаления: снос каталога, на который ещё ссылается агент, ломает раны. Смягчение — обязательный проход через существующий fail-closed скан ссылок и блокировка при непустом boundAgents. Также затрагивается путь секретов, где действуют локи ротации (withAccountHomeSecretMutationLock).

**Фаза 3 — риск реальный.** Для Claude в sandbox-лане явный CLAUDE_CONFIG_DIR с host-путём вне рабочей директории сейчас сознательно игнорируется: acp.ts:265 пишет предупреждение в stderr и подставляет управляемый company-seed, потому что host-путь не виден изнутри sandbox. Чтобы выбор учётки работал и там, нужно стейджить дом внутрь по образцу Codex (acp.ts:226). Это изменение auth-пути, где регресс означает «агенты перестали аутентифицироваться». Делать по одному вендору, за флагом, с прогоном существующих auth-тестов.

**Горячие зоны, которые не трогаем:**

- packages/adapters/codex-local/src/server/codex-home.ts — allowlist isManagedCodexHomePath: он решает, управляемый дом или внешний оверрайд, и от этого зависит, сеет ли Paperclip креды;
- packages/adapters/codex-local/src/server/auth-precedence.ts;
- packages/adapters/codex-local/src/server/acp.ts:226 — репойнт CODEX_HOME в sandbox;
- packages/adapters/*/src/server/adapter-auth-promotion.ts — решения C и H и их локи;
- ротационные локи в server/src/services/secrets.ts.

**Организационный риск.** Репозиторий — чистый upstream paperclipai/paperclip. Выбранная модель поставки — форк с регулярным ребейзом, поэтому дизайн заточен под минимум правок в существующих файлах: три-четыре новых файла плюс две точечные правки (встраивание в AgentConfigForm и замена хардкода префикса в agents.ts).

## 6. Тестирование

- юнит-тесты readIdentity на фикстурах auth.json и .claude.json, включая битые и частичные файлы;
- тест листинга: секреты без метаданных, метаданные без секрета, произвольный путь в конфиге агента;
- тест удаления: отказ при boundAgents больше нуля и при любой ошибке резолва секрета (fail-closed);
- тест пикера: выбор строки формирует один PATCH с обоими полями; агент с произвольным путём не перетирается;
- прогон существующих auth-тестов адаптеров как регрессионной сетки перед каждой фазой.
